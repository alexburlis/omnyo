# Project actions

Persistent, agent-editable project shortcuts in Omnyo’s top-right chat header. The first two actions are visible; extras use an overflow menu. Phone widths draw no header control: every thread actions menu (the `•••` in the header, a sidebar row's menu) has a Project actions item for the open project, with one choice per action showing its status, to run it or force quit a running command (the Force quit choice turns into a Confirm force quit choice for six seconds first; a failed run shows an error toast). Wider touch screens show one Actions control that opens every action. The header overflow control is a labelled More chevron, never a second `•••`. Configuration belongs to the project, not a chat.

Use the `project_actions` native tool or `omnyo project-actions list/replace/run`. List first, then replace the whole ordered list with its optimistic revision. No actions are seeded automatically. Supports exact host command argv, HTTP(S) URLs. Commands have a bounded timeout (up to 12 hours) and expose exit status, never stdout/stderr. A clicked button shows a spinner while its command runs, a check when it succeeds and a warning when it fails.

While a command runs, its button shows the elapsed time and a progress strip. A command reports live status by writing lines to the file named in `OMNYO_ACTION_STATUS`, for example `echo "2/4 Building" > "$OMNYO_ACTION_STATUS"`. The host reads that file every second. The last non-empty line becomes the status, at most 160 characters, and a leading `current/total` fills the strip by step. A command that never writes there shows an animated strip and `Running`. Hovering or focusing a running button shows the status and elapsed time; in the overflow menu the status appears under the action; on compact screens the choice shows it beside the label. Only the lines a command writes to that file leave the host. A running command also shows a × that asks for confirmation, then force quits the whole process tree (SIGTERM, then SIGKILL after three seconds); `omnyo project-actions stop ID` does the same. No LLM or paid provider is called when a button runs.

A command action can carry a status check, `check: {argv, intervalMs}`, for what the action starts or manages, such as an app it launches. The check runs `argv` on the action's machine and folder every `intervalMs` (default 5 seconds, from 2 seconds to 10 minutes) while a header showing the action is visible, and right after the action finishes. It must answer within 10 seconds. Its exit status sets a dot on the button: 0 green (running and current), 1 hollow (not running), 2 amber (running, but the action would change something, such as loading a newer build); any other exit, a check that cannot start, a timeout or an unreachable machine draws a dashed dot. The last line it writes to `OMNYO_ACTION_STATUS` is the text shown on hover, and `list` returns each check's tone, text and start time (`checkedAt`) as `states`. A check nobody has polled for two intervals plus 10 seconds is left out; agent and CLI listings wait for any due check, so they always show a current one. While the action itself runs, its running status replaces the dot. Several headers showing one project share one check per interval.

Development: `pnpm install`, `pnpm typecheck`, `pnpm test`, `pnpm lint`, `pnpm format:check`, `omnyo plugin build`. Anti-slop policy uses the vendored rules in `tools/oxlint/anti-slop`.

Project actions keep the last loaded labels across header remounts and chat reactivation while refreshing in the background. Each project has its own observable snapshot. Failed refreshes remain visible instead of clearing saved actions.
