### ISS-003 — The per-row callback source state reports idle or stopped while the source runs background commands or workflows, disagreeing with the thread work view

- **Priority rationale.** This is a bounded correctness defect with no data loss. It shows wrong status text and wrong status data on four surfaces: the native callback card says "The source chat has stopped working.", the agent's runtime instructions carry sourceState "idle", the ask-user-question sidebar marks the link as blocked, and source-change forwarding skips the owner-thread notification. Exposure is limited to callbacks whose source thread is idle but still has a running background shell command (local_bash) or a running workflow (local_workflow). That is a realistic Claude Code pattern, but the callback itself still completes correctly on its marker. Reconciliation (reconcileThreadCallbacks) matches events and never reads sourceState. The user can work around it by opening the source chat. This does not meet the P1 bar of high-impact broken core behavior.
- **Affected.** Paths are at commit e9e1b74c3b906edbf2d4b4c3da8f930c62e24f9e. - **Per-row reader.** packages/db/src/data/thread-attention.ts: getCallbackSourceState L85-128, toThreadCallback L130-142 and listThreadCallbacks L144-164. - **Batch reader.** The same file, readThreadAttentionFacts L214-363. - **Consumers of the per-row reader:**   - apps/server/src/services/interactions/thread-attention.ts: notifyThreadAttentionChanged L88-98 (the hub attentionItems payload) and threadAttentionSnapshot L186-193 (GET attention snapshot). The snapshot feeds the native UI in apps/app/src/components/thread/user-questions/NativeThreadAttention.tsx NativeCallback L251-261 and the ask-user-question plugin through sdk.experimental_attention.snapshot, in plugins/ask-user-question/src/sidebar/callback-waits.ts L4 and callback-links.ts buildLinkGraph L63.   - executeAttentionCommand L228 in the same service file.   - apps/server/src/routes/thread-attention.ts: the per-thread route at L42 and the source-change forwarding at L105-114 (toThreadCallback at L107).   - apps/server/src/services/threads/thread-runtime-config.ts L314-337, the "Native callback dependencies" agent instructions. - **Consumers of the batch reader:** apps/server/src/services/threads/thread-work.ts buildThreadWorkSummaries L497, with callback evidence at L688-698, and apps/server/src/services/threads/thread-runtime-display.ts L658. - **Who sees it:** every user whose callback source chat ends its turn while a background Bash command or workflow keeps running, mainly Claude Code sources that use run_in_background or workflows.
- **Expected and actual.** **Expected:** a callback has one source state on every surface. The thread work view (thread-work.ts L688-698) already uses the batch reader and tells the user "<source> is working and will return a result." whenever that reader says "working". The batch reader counts activeBackgroundAgentCount, activeBackgroundCommandCount and activeWorkflowCount (L320-328). That shows the product treats an idle thread with a running background command or workflow as working. **Actual:** getCallbackSourceState checks only `row.activeBackgroundAgentCount > 0` (L108-110). It ignores activeBackgroundCommandCount (which counts local_bash tasks, per events.ts L3407-3415) and activeWorkflowCount (local_workflow). For an idle source with only such a task, the per-row reader returns "idle" while the batch reader returns "working". The consequences: - NativeCallback shows "The source chat has stopped working." - buildLinkGraph sets blocked=true, because the state is neither working nor waiting. - The agent instructions serialize sourceState "idle". - The forwarding in routes/thread-attention.ts L105-113 compares per-row states. Starting or ending such background work leaves the per-row state "idle", so notifyThreadAttentionChanged is not called for the owner thread. **A second disagreement, about precedence:** - In the per-row reader, a queued message waiting on an interaction yields "needs-input" only after the error and working checks (L104-125). So error beats it, and working beats it. - The batch reader adds a queued interaction to needsInput before both checks (L312-317, then L344). So "needs-input" beats both "error" and "working". A source that has errored, or is active, and also has a queued interaction-wait message therefore gets "error" or "working" from the per-row reader and "needs-input" from the batch reader.

That fixture used an in-memory SQLite database with an idle source and one running background shell command, and printed {"callbackList":"idle","attentionFacts":"working"}. The fixture is in docs/2026-11-25-material-simplification-audit.md L206-250. To confirm in packages/db tests: 1. Create an owner thread and an idle source thread. 2. Insert a threadCallbacks row from the owner to the source. 3. Append item/started for a backgroundTask item with the local_bash task type, or local_workflow. 4. Compare listThreadCallbacks(db, owner.id)[0].sourceState with readThreadAttentionFacts(db, [owner.id]).get(owner.id).callbacks[0].sourceState. Expect "idle" and "working". For the precedence case, set the source status to "error" and add an unfailed queued message whose waitingOn kind is "interaction".
