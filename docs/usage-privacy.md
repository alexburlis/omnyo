# Coordinator usage choices

This document describes the local implementation. It does not certify a deployed ingress, a published app or the retention settings of an external provider. Older installed versions can still send legacy telemetry until upgraded. The no-collection public beta remains disabled.

The coordinator has two independent purposes. The weekly count measures participating active coordinator installations, not people. Product analytics measures only activity from a client that has explicitly opted in. A shared coordinator cannot use one person's choice as another person's grant.

## Controls

Settings → General has **Weekly activity count** and **Product analytics for this client**. The first choice applies to the coordinator. The second creates a random consent capability for that browser. The browser retains the capability as a consent record and sends it only to the coordinator's allowlisted usage and contributing action endpoints. Clearing browser storage loses that browser's proof and ability to request early erasure; raw records still expire after 30 days.

```
omnyo settings usage status --json
omnyo settings usage count on
omnyo settings usage count off
omnyo settings usage analytics on
omnyo settings usage analytics off
omnyo settings usage preview --json
omnyo settings usage erase
```

The CLI stores its per-coordinator consent record with owner-only permissions in the data directory's `client-usage` folder. Only interactive CLI sessions contribute behavioral activity. Scripts, automations, agent callers, child chats, boot and idle work do not qualify. The CLI never prints the capability. The erase command retains proofs when the collector is unavailable, so it can be retried.

`OMNYO_TELEMETRY=false` is a pre-start veto for both purposes. There is no default collector: `OMNYO_USAGE_COLLECTOR_URL` must explicitly name the first-party origin. Development and no-collection builds remain disabled. An old saved false declines both purposes; an old true grants neither. A legacy CLI true cannot grant product analytics. A new explicit purpose choice can replace the corresponding refusal.

A bare coordinator has an unknown region and asks first. `OMNYO_USAGE_COUNT_REGION=US` is an installer-maintained jurisdiction hint, not an IP lookup or caller header. The US regional default becomes eligible only after the app shows the notice and the user chooses Continue; Turn off is equally available. Until then the count is off. All other regions remain ask-first. Product analytics always requires a separate affirmative client grant.

## Wire and retention dictionary

| Request or field                           | Meaning and bounds                                                                                                                                                                                                                                                                                                             | Local and receiving storage                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| `POST /metrics/active-week`, empty body    | One attempt after a successful human new chat or message in a newer UTC ISO week. Fixed method, path, headers and agent string; no ID, timestamp, period token or dimensions.                                                                                                                                                  | The coordinator retains only its highest attempted week. The collector retains weekly counts. |
| `subject`                                  | SHA-256 of 32 random bytes, scoped to one client grant. No account, host or provider identifier is an input. A new grant after withdrawal rotates it.                                                                                                                                                                          | Consent proof remains local; receiver raw records expire after 30 days.                       |
| `day`                                      | UTC day, without a client event timestamp.                                                                                                                                                                                                                                                                                     | Raw expiry at the receiver; local counters retain only the current day.                       |
| `count`                                    | Cumulative count for a subject/day/event/property combination, capped at 100; activity is capped at one. The receiver upserts the largest value.                                                                                                                                                                               | Bounded local daily counters, then receiver raw expiry.                                       |
| `activity`                                 | First eligible human action of each day; `first` is true only on the first attempted activity report of this grant.                                                                                                                                                                                                            | Supports matured D7/D28 cohorts without treating returning old subjects as new.               |
| `first_accepted_action`                    | Once per client grant, time to the first accepted human chat/message: `under_1m`, `1_to_10m`, `10_to_60m` or `over_60m`. This is not model reply time; unknown or backwards timing is omitted.                                                                                                                                 | Raw expiry; exact elapsed time is never sent.                                                 |
| `feature_used`                             | Only the observed `chat`, `queued_message` and `plugin` features. No plugin inventory, name or catalog identifier.                                                                                                                                                                                                             | Daily capped count.                                                                           |
| `public_plugin_installed`                  | Only explicit builtin or verified Omnyo catalog installation of `workspace-github` or `sentry`. No private IDs, inventory or silent reconciliation.                                                                                                                                                                            | Daily capped count.                                                                           |
| `onboarding`                               | Fixed step, outcome and first-run/replay enums. No rendered text or DOM.                                                                                                                                                                                                                                                       | Daily capped count.                                                                           |
| `operation`                                | Fixed operation, outcome and latency bucket. Setup failures use only `nonzero_exit`, `start_rejected` or `unknown`; no command, exit code or error text. Actual thread HTTP requests measure successful and failed latency. Provider identity is not reported because these operation boundaries do not reliably establish it. | Daily capped count.                                                                           |
| `POST /metrics/product-erasure`, `{proof}` | Explicit authenticated erasure by possession of the client capability. The proof is in the body, never a URL.                                                                                                                                                                                                                  | Withdraws locally before sending; pending/complete state is retained for retry.               |

Product reports coalesce locally and drain on fixed UTC hour boundaries through the existing coordinator sweep, never immediately after an action or on page unload. Each interval sends only the latest cumulative value for each subject/day/category. Pending batches drop on withdrawal, shutdown, stale days or failed dispatch; they do not retry. Startup discards increments that never reached a scheduled dispatch, so shutdown can undercount. This limits connection timing to the hourly collection window.

Product events omit prompts, messages, thread and account IDs, provider slugs, exact OS/build data, URLs and filesystem paths. Core action endpoints and the SDK use the same coordinator boundary. Unknown fields and unregistered values are rejected before serialization. A local preview uses synthetic safe fields and sends nothing to the collector.

The count reserves its week atomically before sending. Failure, cancellation and an ambiguous response consume that attempt; there is no retry or backfill. Off/on in the same week does not repeat it. Receiver UTC week may differ at a boundary. HTTPS operators can see connection metadata; aggregate-only claims require a separately verified deployment with no request-level logging. This unauthenticated count is an internal trend and cannot establish public popularity or billing.

Withdrawal invalidates in-flight requests and local pending data. A completed delivery cannot be recalled by aborting it. Erasure is a separate explicit operation. Non-identifying aggregate rollups cannot be tied back to a proof. Local and collector tests use synthetic input; external storage, exports, backups and historical deletion remain separate approval and verification work.
