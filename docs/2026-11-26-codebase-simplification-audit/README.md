# Omnyo codebase simplification audit

Machine-specific checkout paths, hostnames and IDs use portable names in this copy. The original audit files retain the local evidence.


The audit identifies ways to remove maintained code and duplicate rules while preserving supported behavior. Its implementation cards also record the cases where product decisions, compatibility evidence or separate bug fixes must come first.

## Snapshot and support scope

- **Revision.** Public Omnyo at `e9e1b74c3b906edbf2d4b4c3da8f930c62e24f9e`, the detached snapshot prepared by the original audit. `origin/main` and the working checkout advanced separately. Reconfirm the cited paths, callers and behavior before starting any card.
- **Sources.** The tracked inventory contains 9,754 paths. The team followed representative implementations and consumers across the apps, packages, plugins, public site, release tools, test harnesses and assets. The [November 25 audit](../2026-11-25-material-simplification-audit.md) supplied 20 leads. The coverage notes record the paths checked, depth and limits.
- **Support contract.** Preserve macOS/Linux, WSL2 and the alpha Windows host, the mobile native shell and PWA, desktop shell and packaging, CLI, public SDK, independently forkable plugins, persisted data, upgrade paths and developer/recovery commands. Preserve interface behavior, accessibility, timings, cleanup, order, error semantics and public identifiers. The snapshot's `docs/platform-support.md`, `docs/provider-plugin-api.md`, `docs/forkable-plugins.md` and `DESIGN.md` establish these boundaries.
- **Recovery.** The first audit ran through Claude's native Workflow tool and ended at the weekly limit. One of its 22 sweeps returned a structured result. The continuation recovered that result as evidence, then inspected the snapshot along four lanes. The original workflow did not finish its merge, card or review phases.
- **Baseline.** The snapshot had no `node_modules`. Current evidence comes from source inspection, Git blob comparisons, line counts and two isolated parser checks with synthetic fixtures. Product suites, device tests, native/provider parity, production measurements and before/after performance comparisons remain implementation checks. Private workflow configuration and downstream/private consumers are outside the public snapshot.

## Method and comparison basis

Use maintained rules and coordination costs when ranking. The byte-identical scan found 32 groups and 5,926 duplicate lines across tracked TS, TSX, JS and MJS source groups of at least 15 lines. Tests and named fixtures account for 3,840 of those lines. Binary assets, generated/vendor output, deployment configuration and test changes are outside projected handwritten production savings. The remaining duplicate lines are leads. Some packages deliberately maintain separate protocols or provider variants despite similar source. Each card states which boundaries are worth preserving.

## Ranked opportunities

Classic ACP has the largest potential reduction because retirement removes an engine, a plugin and their ongoing parity work. Supported session continuity and public SDK consumers make it conditional. Provider usage is the strongest direct refactor. Both engines and both native provider plugins currently maintain the same core collection policy. The server retention and callback changes rank highly because inconsistent ownership has already produced different behavior.

## Implementation sequence

1. Start with contained removals and extractions. The obsolete primary-history APIs and Explore vocabulary can be scoped independently. Provider usage has its own focused cache and refresh checks, and can run independently of the server changes.
2. Choose the ACP support direction before extracting duplicated ACP-specific code. If both engines remain supported, reuse the same native-root resolvers and equivalent pure helpers through the packed SDK. Classic retirement would absorb much of that saving. The per-provider usage owner still benefits the surviving engines.
3. Establish the expected retention and callback behavior in synthetic host/DB fixtures before consolidating either path. Keep the changed behavior separately attributable. Share an inbox read snapshot only after checking owner overlap, batching and real query counts. The callback and inbox changes may touch shared raw facts and must count the same saving once.
4. Characterize client behavior before touching cross-surface timing or state. Composer, realtime and panels need their own order, error and UI checks. The same rule applies to separate packaging/runtime identity in desktop release channels.
5. Keep retirement plans gated by the supported callers. This includes source-rename recovery, lab preview ownership and ACP parity. Measure removal from the final authorized keep list and exclude moved code, live compatibility shims and test fixtures from production totals.
