# Built-in browser automation

`omnyo browser` is the experimental core API for automation integrations controlling Omnyo desktop tabs. The Browser Automation plugin adds its own script/session commands; another plugin can use the same core connection independently.

`omnyo browser-automation open --machine <name-or-id>` accepts an exact host ID or an unambiguous machine name. Exact IDs take precedence; unknown or ambiguous names fail before session creation. Use `--backend local --headless` for headless sessions or `--backend desktop --desktop <instance-id>` for a desktop session.

Tab/control operations target `--host <host-id> --instance <instance-id> --generation <generation> --thread <thread-id>`. `--thread` defaults to `OMNYO_THREAD_ID`. Omit `--instance` and `--generation` (and optionally `--host`) to use the only Omnyo desktop window connected on the given host, or on all connected hosts; the command fails and lists the candidates when there are several, none, or a host cannot be checked. Pass `--instance` and `--generation` together, with `--host`. `omnyo browser instances --host <host-id> --json` lists one host's windows. The browser host can differ from the agent host. Never guess between desktop windows.

A desktop window connects to the host daemon on its own machine only when that daemon is enrolled with the server the window is using. The addresses match, or both report the same server launch at `/health`. The second case covers a coordinator machine whose daemon uses loopback while the desktop app uses a public address. A relay address cannot prove the server's identity, so a desktop app that reaches its own machine's server through the relay lists no windows.

To show a page served over HTTP to the user, run `omnyo browser create --url <http-url> --reveal` inside the thread. The native browser loads only HTTP(S) URLs; open a local HTML file with `omnyo thread open <file.html>` instead. Both reveal routes widen the side panel to at least 60% of the window.

- `tabs`: list native tabs and their control state.
- `profile-renderer [--duration <duration>]`: explicitly capture the selected Omnyo app shell's JavaScript CPU activity, with a default of 2s and a range of 200ms..5s. Uses the desktop window flags without `--thread`; this profiles the app shell, not a browser tab. Returns bounded app asset paths, source coordinates, sample counts and fixed engine categories, with no function names, page content or full URLs. It preserves focus and background throttling, refuses an attached debugger, and reports unsupported on older desktop clients. It neither reloads the window nor installs an update. SDK: `experimental_desktopBrowsers.profileRenderer`.
- `create [--url <http(s)-url>] [--reveal]`: create a tab in the Omnyo browser profile, with the user's signed-in cookies. Defaults: hidden, about:blank.
- `acquire <tab-ids...> --controller <label> [--ttl-ms <ms>]`: acquire exclusive tab control. If the owning thread is already focused, open the side panel and select the first tab. New or activated CDP tabs follow the same rule. No thread switching or desktop window activation. Default expiry is five minutes, maximum thirty minutes. Controlled tabs carry the Omnyo browser profile's signed-in authority.
- `connection <lease-id> --output <new-file>`: write private connection JSON with mode 0600 on the CLI host. The loopback WebSocket endpoint is usable only on the browser host. Pass it privately to an integration worker; never expose it through a shared port or chat output.
- `release <lease-id>`: revoke automation while keeping tabs open.
- `reveal <tab-id>`: open the side panel, widen it to at least 60%, and select the existing native tab only if its thread is already focused; otherwise leave the current view unchanged.
- `capture <tab-id> --output <new-file>`: save a bounded JPEG to the CLI host without focusing the tab.
- `close <tab-id>`: explicitly close that native tab.
- `watch`: print changed tab snapshots every two seconds until interrupted. Disconnects report errors; this is not a lossless event log.

Cookie import copies signed-in sessions from a browser installed on the desktop host into the Omnyo browser profile. These commands take the same desktop-window flags and defaults but no `--thread`:

- `import-sources`: combine known-browser entries (Chrome, Chromium, Helium (macOS), Edge, Brave, Vivaldi, Opera, Arc (macOS), Dia (macOS), Firefox, Zen, Safari (macOS)) with automatically detected Chromium/Firefox cookie stores, their profiles with cookie counts, and why one is unavailable (`notInstalled`, `browserRunning`, `needsFullDiskAccess`, `needsKeychainApproval`, `unsupportedPlatform`). On macOS the result also carries `recommended` (`sourceId`, `sourceProfileDirectory`): the system default browser's last-used profile (Firefox: the installation's default profile), or its profile with the most cookies when the browser records none. It is omitted when the default browser is unsupported, unavailable, or cannot be read. Text output prints it as `Default browser: --from <id> --profile <directory>`, ready for `cookie-sync enable`.
- `import-cookies --from <source-id> --profile <directory>`: read that profile's cookie store and write it into the Omnyo browser profile. Firefox, Safari, and Chromium browsers on Linux must be quit first; Chromium browsers on macOS (including Dia and Chrome) can stay open. macOS prompts for Keychain access for Chromium browsers and needs Full Disk Access for Safari. The result reports imported and skipped counts plus skipped hosts; `ok: false` carries a reason. A one-time copy, never a sync; partitioned cookies and non-default Firefox containers are skipped. Desktop only (macOS and Linux). Use the exact source ID returned by `import-sources`; additional stores have stable opaque `storage-…` IDs.
- `cookie-sync status`, `cookie-sync enable --from <source-id> --profile <directory>`, `cookie-sync disable`, `cookie-sync run`: keep the Omnyo browser signed in from one source profile. Enabling syncs immediately, then every 15 minutes and when an Omnyo window opens if the last sync is over two minutes old. Each sync imports the profile's live cookies and removes cookies Omnyo previously synced that the source no longer has, so signing out in the source signs out Omnyo; cookies Omnyo did not import are never removed. `disable` stops syncing and keeps imported cookies. The result reports the source, `lastRun` (imported, removed, and skipped counts, or `ok: false` with a reason), and `nextRunAt`. Cookie values, names, and hosts never leave the desktop host: reading and writing happen in the desktop app, and its state file in the desktop app's data directory stores no cookie values. Running `enable` again with another source switches to it; the next sync removes cookies synced from the previous profile that the new one lacks. Settings → Browsers → Keep logins synced is the same control, with a Sync from dropdown for choosing the browser profile and, while sync is off, a Connect button for the `recommended` profile. Desktop onboarding on macOS and Linux has a Browser step that connects the recommended profile, or another detected one, in one click; skipping after a failed connect turns sync back off. Agent CDP sessions cannot read cookies (`Network.getCookies`, `Network.getAllCookies`, `Page.getCookies`, and `Storage.getCookies` are refused) and cookie headers are removed from forwarded network events; page scripts can still read `document.cookie`.

Discovery checks cookie database schemas in macOS Application Support, Linux configuration directories (honoring an absolute `XDG_CONFIG_HOME`), hidden home directories, and Flatpak/Snap data directories. Known entries take precedence and retain browser-specific encryption settings; canonical database paths deduplicate additional stores. Discovery does not read encryption secrets. Unknown sources must match a browser application registered for HTTP and HTTPS (and the WebBrowser category on Linux); cookie databases belonging to other applications are excluded. Names are matched against macOS bundle metadata or Linux desktop-entry metadata. Standard user/system application directories and Flatpak/Snap desktop exports are checked. Known-browser entries remain available if application registration is missing. Additional profiles are labeled with their detected storage family.

Scanning is bounded (2,000 directories, 100 additional stores, 100 profiles per store; three directory levels in standard locations and five inside Flatpak/Snap data). Omnyo's own desktop profile is excluded. Arbitrary custom locations, other cookie formats, and custom encryption are not universally supported. Additional Chromium stores use matching known encryption metadata when available, otherwise the directory name with the conventional macOS `<name> Safe Storage` / `<name>` Keychain identity or Linux keyring application name. A missing key reports an import failure; unsupported versioned encryption is skipped. Refresh rescans, and import resolves discovered IDs again before reading a selected profile.

All commands support JSON output. In plugin code use `api.sdk.experimental_desktopBrowsers`; the Plugin Guide documents the typed surface. Stop/Take over revokes native control; stopping the owning thread also releases its server control leases. Old connection generations cannot control replacement windows.

Cloud browsers are not supported. Headless Chrome on an enrolled host belongs to the Browser Automation plugin.
